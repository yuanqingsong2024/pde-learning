PDE 学习站：从全栈开发到 PDE 解决方案工程师

Prompt-Driven Engineering：把 Prompt 当软件构件来做，而不是当聊天咒语来写。

核心目标：每个 Prompt（或一组 Prompt）都要结构清楚、行为稳定、能测、能改、能复用。解决方案工程师交付的不是一段文本，而是一个可回归测试、可回滚、可审计、可算成本的系统。

面向读者：Java、Web、小程序背景的全栈开发工程师 / 开发负责人，目标是 PDE 解决方案工程师。本站内容整合自 2026-10-28 的调研报告，关键来源见文末；PDE 不是偏微分方程。

PDE 是什么

术语提醒：检索未发现 PDE / POG 的统一官方标准定义，本站按工作定义使用：PDE 是端到端的解决方案工程学科，POG 是其中负责治理的一层。对外沟通时先亮明定义，可优先使用 AI Solution Engineer、LLM Engineer、PromptOps / LLM Governance 等更通用的说法。
概念核心问题典型产出
Prompt Engineering这一次怎么写才答得好系统提示、Few-shot 示例、输出格式约定
PDD（提示驱动开发）开发循环快不快：意图 → 生成 → 评估 → 迭代规约式提示 + 测试用例 + 迭代后的代码
PDE（本文工作定义）这个 Prompt 本身质量够不够，业务目标如何变成可靠系统方案设计、提示资产、评测集、部署与治理全套
POG / PromptOps全公司怎么管、复用、审计这些资产提示目录、版本与别名、审批流、审计日志
上下文工程模型每一步看到什么信息检索策略、分块与排序、记忆分层、上下文预算

最优先的三件事：（1）做一个带结构化输出 + 黄金评测集的 RAG 问答；（2）做一个带工具调用 + 人工确认的审批型工作流；（3）把提示入库、版本化、接可观测，形成可展示的解决方案交付物，而不是一堆聊天截图。

解决方案工程师的一天

  1. 发现：区分能用规则/搜索解决还是必须用 LLM；定义成功指标、收集真实语料与合规边界。交付：用例画布、成功指标、风险与数据清单。
  2. 方案设计：画架构、选模型分层、定 Token / 延迟 / 成本预算。交付：架构图、选型表、预算。
  3. 提示架构：写系统提示、拆分路由/抽取/综合/评审提示、定 JSON Schema 与工具 Schema。交付：带版本的提示模板库。
  4. 评测：建黄金集、跑基线、做回归与失败分类。交付：评测报告、回归门禁。
  5. 部署：灰度与别名切换、降级策略、限流与成本熔断。交付：发布清单、回滚方案。
  6. 治理（POG）：PR 式评审、审批、审计、定期复审过期提示。交付：提示目录、变更日志、审计记录。
  7. 运营复盘：看成本、延迟、失败率与用户反馈，向业务方汇报质量-成本-延迟三维结果。

关键判断：先找最简单的解法，只有在需要时才增加复杂度。单次调用 + 检索能解决的不要上智能体；步骤固定用工作流；步骤不可预知才用智能体，并加步数上限与护栏。

通用参考架构与五个必会用例

用户（Web / 小程序 / 客服工作台）→ 鉴权 + 限流 → API 网关 / BFF（Java Spring Boot）→ 提示注册表 + 模型路由 + 成本熔断 → RAG 检索（权限过滤 → 混合检索 → 重排）+ 工具调用 → LLM 调用（结构化输出，超时 + 重试上限）→ 输出校验（Schema → 规则 → 安全 → 证据）→ 自动执行 / 人工确认 / 转人工 → 业务系统 + 审计日志 + 可观测

Java 落地要点（已核验文档）：Spring AI 提供跨厂商 Chat / Embedding API、结构化输出到 POJO、向量库、工具调用、可观测、RAG 与 MCP；LangChain4j 提供统一 LLM / 向量库 API、AiServices、Agent 与 RAG 工具箱。已在 Spring 生态优先 Spring AI；需要更丰富的 Agent 语义可看 LangChain4j，不要在同一个服务里混用两套提示与追踪体系。

用例模式评测要点
客服助手路由 → RAG → 带引用草稿 → 人工确认；退款等高风险强制转人工引用准确率、拒答与转人工恰当率、客服采纳率、注入测试
代码评审 / 开发助手并行评审（安全、性能、可读性、测试）→ 聚合去重 → 结构化评论，不自动合入检出率、误报率、严重度准确率、行号有效率
文档 / 知识问答摄入 → 分块 → 混合检索 → 重排 → 带引用生成 → 证据校验Faithfulness、答案相关性、上下文精度/召回、引用准确率、拒答恰当率
数据分析与报告查询计划 → 白名单 SQL 校验 → 只读执行 → 结构化报告；模型不直接写生产库SQL 可执行率、结果正确率、口径错误率、数字与图表一致率
工作流自动化编排者-工人或固定工作流 + 状态机，断点续跑、幂等、失败转人工工具选择与参数正确率、步数、循环检测、端到端成功率

选型速查：一次检索 + 一次生成能解决 → 单次调用 + RAG；步骤固定 → 固定工作流；步骤取决于输入 → 智能体（带上限与人工确认）；写操作、资金、合规承诺 → 工作流 + 人工确认。

作品集：6 个项目

每个项目必备：README（业务问题、架构图、成功指标、成本/延迟数据）、prompts/（版本化模板 + 变更说明）、schemas/、evals/（黄金集 + Rubric + 回归报告）、脱敏追踪、可观测截图、governance.md（负责人、审批、回滚步骤）。没有数字的项目，在解决方案工程师面试中说服力会大打折扣。

  1. 企业文档问答（RAG，最优先）：Spring Boot + 向量库，100 篇文档，权限过滤，流式 Web 问答；50 条黄金集，含干扰、过期、无答案陷阱。
  2. 客服 Copilot：意图路由 → RAG → 草稿 → 人工确认，高风险强制转人工；按意图切片的采纳率与转人工恰当率。
  3. 代码评审助手：PR diff 分块 → 并行评审 → 聚合去重 → 结构化评论；不自动合入。
  4. 数据问答与报告生成：自然语言 → 查询计划 → 白名单 SQL 校验 → 只读执行 → 结构化报告；拒绝写语句测试。
  5. 审批型工作流智能体：分类 → 抽取 → 校验 → 审批确认 → 执行 → 审计，断点续跑与幂等；轨迹评测。
  6. 提示治理平台（POG 最小实现）：目录、版本与别名、PR 评审、审计日志、灰度与回滚演练；可复用前五个项目的提示。

面试 30 秒叙事：业务问题是什么 → 为什么选这个架构而不是更复杂的智能体 → 提示与 Schema 怎么设计 → 评测集、基线与改进数字是多少 → 上线后成本、延迟、失败率是多少 → 如果重做会改哪里。

反模式与自查

  • 无评测就上线；提示写进业务代码字符串；原地修改生产提示；上下文无脑堆料。
  • 只在提示里要求 JSON，不用 Schema / 校验；Schema 通过就以为值正确；检索错了怪模型、模型错了换更大模型。
  • 过度依赖 LLM-as-Judge；给智能体过大权限、无停止条件；把用户输入、检索文档、工具返回都当作指令。
  • 系统提示、密钥、内部规则泄露到客户端 / 日志；无成本、延迟预算与熔断；先上智能体，再证明必要性。
  • 只测“好问题”，不测拒答、干扰、过期、无答案、越权、注入五类负例。

每两周自查：能不看资料画出 RAG + 工具 + 评测 + 治理架构图吗？每个项目都有黄金集、基线与回归报告吗？能说出单任务成本、P95 延迟、最常见的 3 类失败吗？提示都在注册表里有版本、负责人与回滚步骤吗？写过至少 20 条注入 / 越权 / 拒答负例并让它们进回归吗？
